# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Sway" is a static HTML/CSS/JS site cataloguing artistic swimming figures and elements by age/discipline category. There is no build system, package manager, or test suite — it's plain HTML files with one shared `style.css` and one shared `script.js`, meant to be opened directly or served as static files (e.g. `python -m http.server` from the repo root).

## Site structure

- `index.html`, `library.html`, `search.html`, `figures.html`, `elements.html`, `contact.html` — top-level pages, root-relative links (`style.css`, `figures/...`). `figures.html`/`elements.html` each show a breadcrumb plus `.category-features` — one full-width `.category-feature` row per category (icon medallion, count, title, blurb, a preview of a few tricks, a "Browse" link). This is deliberately *not* the small `.category-grid`/`.category-card` tile grid `library.html` uses — with only 3 or 4 items, that tile grid left most of the page empty, so these two pages get their own richer, always-full-width component instead. See "Breadcrumbs & the regeneration script" below for how the counts/blurbs/previews are generated.
- `figures/` — one hub page per age category (`10u.html`, `12u.html`, `youth-13-15.html`) plus one page per individual figure.
- `elements/` — one hub page per discipline category (`solo-technical.html`, `duet-technical.html`, `mixed-duet-technical.html`, `junior.html` = Team Technical) plus one page per individual element.
- `assets/` — placeholder images for a handful of figures, named after the figure (e.g. `Saturn.png`, `Venus.png`). Most figure/element pages do not yet have a real image.
- `search-data.json` — hand-maintained flat index (`title`, `url`, `category`) of every figure/element page, powering both the header/hero autocomplete and the `search.html` results page. **Any new or renamed skill page must be added/updated here too**, or it won't be searchable.
- `script.js` — vanilla JS, no framework, no modules. Independent IIFEs, each a no-op if its target element is missing: scroll-reveal via `IntersectionObserver`; the mobile `.nav-toggle` hamburger (toggles `.nav--open` + `aria-expanded`, closes on link click); making the header `Library ▾` button itself navigate; header scroll-state toggling; a shared `fetch('search-data.json')` loader (paths in the index are root-relative, so code running from inside `figures/`/`elements/` prefixes `../`); an autocomplete dropdown that attaches to every `.search-form__field` (currently only the library/search hero search bars — the compact header `nav-search` box uses a different class and does *not* get autocomplete, it only full-submits to `search.html`) and shows up to 6 matches; the `search.html`-only results-page renderer (reads `?q=`); the `library.html`-only media-strip drag (single rAF loop owns the track's transform so drag and idle auto-drift never fight over it); and (index.html only) the pool water simulation described below. Every page includes `[../]script.js` now (see header note below), so none of this can assume it's running on a "special" page — always check for the target element.
- `.github/workflows/deploy.yaml` — deploys the repo root straight to GitHub Pages on every push to `master` (no build step). `.github/copilot-instructions.md` exists but is stale (it describes an old layout where `index.html` lived under `.github/workflows/`; ignore its file-location claims).
- `scripts/sync_pages.py` — a stdlib-only Python tool that regenerates the `search-data.json`-derived parts of the figures/elements hierarchy (breadcrumbs, `figures.html`/`elements.html` category cards, hub-page count/DD-range lines, each individual page's "related tricks" list). See "Breadcrumbs & the regeneration script" below — this is the one exception to "no tooling," kept specifically because those sections would otherwise drift from `search-data.json` by hand.

## Header — identical on every page, at two path depths

Every page in the site — top-level pages, the 7 category hub pages, and every individual figure/element page — shares **one** header markup: brand link, mobile `.nav-toggle` hamburger, `nav#site-nav`, the `Library ▾` mega-menu dropdown (`<li class="dropdown dropdown--mega">` → `<div class="dropdown__mega">` with a `.dropdown__col` per Figures/Elements), a Contact link, and the `nav-search` box (submits to `search.html`). Every page also includes `<script src="[../]script.js" defer>` right before `</body>` (needed for the hamburger, the dropdown-button-click-to-`library.html` fallback, and — on pages that have `.reveal` elements — the scroll-reveal). The only difference between pages is path depth:
- **Root-level pages** (`index.html`, `library.html`, `search.html`, `figures.html`, `elements.html`, `contact.html`) use bare relative hrefs (`figures/10u.html`, `contact.html`, `search.html`, …).
- **Everything under `figures/` and `elements/`** (both the 7 category hubs and every individual skill page) uses the identical markup with every href/`action` prefixed `../` (`../figures/10u.html`, `../contact.html`, `../search.html`, …).

When adding a new page, copy the header verbatim from an existing sibling **at the same depth** — don't hand-roll it, and don't copy a root-level header into `figures/`/`elements/` (or vice versa) without redoing every `../` prefix. This wasn't always one template — root pages, category hubs, and individual pages each used to have their own divergent header (a flat single-column dropdown, no mobile toggle, no search box, or a bare Home/Library/Contact nav with no dropdown at all) until they were synchronized into the single mega-menu version described above.

The footer follows the same two-depth pattern and was synchronized the same way: every page now uses the full three-column `.site-footer__cols` footer (brand/tagline, Explore links, Contact link — with `.reveal` on each column), root-relative on root pages and `../`-prefixed everywhere under `figures/`/`elements/`. It used to be a bare `<p>© Sway</p>` everywhere except `index.html`/`library.html`/`search.html`.

**Known-fixed bug, worth remembering the shape of:** `.dropdown__col .dropdown__menu` (the actual link list nested inside each mega-menu column) needs its own explicit `opacity:1;visibility:visible;pointer-events:auto` in `style.css`. The base `.dropdown__menu` rule defaults those to `0`/`hidden`, and the reveal rule (`.dropdown:hover > .dropdown__menu`) only matches a *direct child* of `.dropdown` — a menu nested inside `.dropdown__mega > .dropdown__col` doesn't qualify, so without that override the mega panel opens as a blank white box (headings visible, links invisible). If the dropdown ever regresses to a "white square" again, check that override first.

### Figure/element hub card grid (all 7 hub pages)

All 7 hub pages (`figures/10u.html`, `figures/12u.html`, `figures/youth-13-15.html`, and all 4 `elements/*.html` hubs — the elements ones were converted from a plain `<ul class="skill-list">` to match) share the same animated `.figure-grid` of `.figure-card` links. Each card is either:
- an `<img>` thumbnail (only where a real asset exists in `assets/` — currently 9 of the 12 `youth-13-15.html` figures), or
- an inline ripple-ring icon fallback (every other card, including *all* element cards, since no element has real artwork) — see the "Ripple-ring icon" note below for why this is inline circles, not a swimmer-pose stick figure or a `<use>` reference.

Element cards also show a `.figure-card__code` ("1A –") and `.figure-card__dd` ("DD 2.7") inline in the title where the skill has them (5 of 28, all in Team Technical, have neither).

Card color/animation-delay variety comes from `nth-child` CSS rules in `style.css` (`.figure-grid > .figure-card:nth-child(4n+1)` etc.), not per-card inline styles — adding/removing cards shifts which rule each one gets, which is fine (it's just visual variety, not meaningful state). Because these pages use `.reveal`, they **must** keep the `../script.js` include (now present on every page, see the header note above) or every card silently stays invisible (`.reveal` starts at `opacity:0` until the `IntersectionObserver` in `script.js` adds `.is-visible`).

All 7 hub pages also carry, inside `.figure-hub-intro`, an `<!-- auto:breadcrumbs -->` trail and an `<!-- auto:hub-meta -->` line ("N figures/elements in this category", plus a "· DD min–max" range on element hubs) — both regenerated by `scripts/sync_pages.py`, see below. The intro paragraph itself is a hand-written one-liner with a regenerator-appended descriptive sentence (also from that script's static category metadata) — edit the one-liner freely, but the appended sentence and everything inside the `auto:` comment markers gets overwritten on the next script run.

### Ripple-ring icon — inline circles only, never `<use>`

The decorative icon used wherever there's no real photo (hub cards' fallback, `.category-feature` medallions, individual pages' `.trick-media__icon-tile`) is three concentric `<circle>`s that ripple outward (`style.css`'s `.ripple-icon`/`rippleOut` animation). It **must** be written as three literal `<circle>` elements inline in the card/tile itself:
```html
<svg class="ripple-icon" viewBox="0 0 100 100" aria-hidden="true">
  <circle class="r1" cx="50" cy="50" r="14"></circle>
  <circle class="r2" cx="50" cy="50" r="14"></circle>
  <circle class="r3" cx="50" cy="50" r="14"></circle>
</svg>
```
This used to be a single shared `<g id="ripple-rings">` in a `<defs>` sprite sheet, referenced everywhere via `<use href="#ripple-rings">` (the same pattern the swimmer-pose icons use, which works fine for *those*). It doesn't work for this icon: browsers don't apply descendant CSS selectors like `.ripple-icon circle` or the `.r1`/`.r2`/`.r3` animation-delay classes through a `<use>` reference's shadow content, so every ripple icon silently rendered as a plain solid black dot (default SVG fill, no animation) instead of animated colored rings. If you ever see a flat black dot where a ripple icon should be, this is why — check that it's inline circles, not a `<use>`.

### Individual trick pages: hero + media, then a details row

Both content layouts share a `<!-- auto:breadcrumbs -->` trail as the first thing inside the outer `<section>`, then a `.trick-hero` (a `.trick-hero__eyebrow` category label + `<h1>`) and a `.trick-media` row of 1-2 `.trick-media__panel`s (flex-wrapped, so one panel centers itself and two sit side by side):
- **Figure pages** (`.figure-split`, 26 pages): the real asset (if any — 9 of 26) is its own panel — these PNGs are official figure *description sheets* (text + diagram + scoring table, not photos), so they're shown at a readable capped width (`.trick-media__panel img`, max-width ~520px) rather than cropped into a fixed box, with a "View full size ↗" link to the original. A YouTube embed (23 of 26 have one, extracted from the page's own linked URL) is a second panel alongside it. A page with neither gets the ripple-icon tile instead. Below the media row, `.figure-bottom` holds `.tips` (coaching-tips placeholder), `.media-links` (every original Instagram/YouTube link preserved verbatim, even though YouTube is also embedded above), and `<!-- auto:related-tricks -->`.
- **Element pages** (`.element-split`, 28 pages): `.trick-media` always shows the ripple-icon tile (no real media exists), with `.trick-hero__badges` (`.element-header__code`/`.element-header__dd`, omitted together on the 5 codeless Team Technical skills) under the `<h1>`. A full-width `.element-sequence` ordered list follows, breaking the name's `" – "`-separated segments into individual steps — then `.element-body` with `.tips` and `<!-- auto:related-tricks -->` (no `.media-links` section at all here; there's nothing real to show, so it's omitted rather than showing an empty-state placeholder).

All internal links from within `figures/*.html` and `elements/*.html` use `../` to reach root assets (`../style.css`, `../index.html`).

## Breadcrumbs & the regeneration script

Every page from `figures.html`/`elements.html` down through individual skill pages carries a `.breadcrumbs` trail (`Library › Figures › 13 - 15 (Youth) › Saturn`) instead of the old "← Back to X" link — plain small text, no `.reveal` (it should render instantly as a wayfinding aid). The current-page segment is unlinked (`aria-current="page"`); for element pages it shows the skill's code (e.g. "2A") when it has one, else the first ~3 words of its name + "…". Segment hrefs follow the same `../`-depth convention as the header nav.

Four sections across the site are **generated, not hand-written** — each wrapped in an `<!-- auto:NAME -->…<!-- /auto:NAME -->` comment pair so `scripts/sync_pages.py` can find and replace exactly that block on a re-run: `breadcrumbs` (every page in the hierarchy), `category-grid` (the `.category-card` grid on `figures.html`/`elements.html`), `hub-meta` (the count/DD-range line on the 7 hub pages), and `related-tricks` (the "More in {category}" cross-links on every individual page). **Never hand-edit inside one of these comment blocks** — it will be silently overwritten the next time the script runs; edit the surrounding hand-written content instead (the `<h1>`, the intro sentence, the tips placeholder, etc.).

Run `python scripts/sync_pages.py` (add `--dry-run` to preview without writing) whenever `search-data.json` changes — a page added, removed, retitled, or recategorized — to refresh all four `auto:` sections from the new data. It's idempotent (re-running with no data changes produces a zero-diff) and self-verifying (it asserts things like: every figure page's original media URLs survive the run verbatim, an element page's parsed code/steps/DD reconstruct its exact original `<h1>` text, and every generated `href` resolves to a real `search-data.json` entry — it fails loudly rather than silently dropping data). It does **not** re-run the one-time structural upgrade that built the `.figure-split`/`.element-split` bodies in the first place (see `upgrade_figure_page`/`upgrade_element_page` in the script) — those already ran once during the initial migration and are idempotent no-ops on pages that already have the new layout, so a new page just needs to follow the existing template (step 1 below) rather than relying on the script to build its body from scratch.

## Pool background system

- `index.html` has a full interactive water simulation: `<canvas id="pool-water">` inside `#pool-bg`, driven entirely by the last IIFE in `script.js` (classic two-buffer ripple/wave algorithm, procedural caustic + tile-grid floor texture with real refraction displacement, cursor and right-click splashes). It's the only page with this canvas.
- Every *other* page gets a matching but static, non-interactive ambient version for free: `body::before` in `style.css` paints a quieter tile-grid + corner vignette using pure CSS, no JS, no markup changes needed on any page. On `index.html` this same `body::before` still exists but is fully hidden — it's the first thing painted inside `body`, so the opaque canvas (a later, real DOM child) always paints over it.
- Swimmer pose SVGs (`swim-star`, `swim-streamline`, `swim-ballet`, `swim-tuck`, `swim-split`, `swim-flamingo`, `swim-vertical`) are defined inline in `index.html`'s `.pool-bg` only — there's no shared sprite file. They used to also appear on the `figures/*.html`/`elements/*.html` hub card grids, but those were all switched to the ripple-ring icon (see below) since it's the site's one generic "no real asset" fallback now.

## Adding a new figure or element page

1. Copy the closest existing sibling page in `figures/` or `elements/` (matching layout — `.figure-split` vs. `.element-split`, both described above) as a starting template, not a hub page. For an element page, name it the same way the existing ones are named: `<h1>` = `{code} – {step} – {step} – ... (DD: n)` (code and DD both optional) — the regeneration script's parser depends on that exact shape if you ever want it to re-derive the sequence/code/DD for you instead of hand-writing them.
2. Link it from the relevant category hub page's `.figure-grid` (copy an existing `.figure-card`, including its `.figure-card__code`/`.figure-card__dd` if applicable — see the card-grid pattern above for the image-vs-icon rule).
3. Add a matching entry to `search-data.json` (`title`, `url` relative to repo root, `category` matching the hub's display name, e.g. `"Figures — 10U"`) — note the `title` here should *not* include the leading code (elements never carry it there, only in the page's own `<h1>`), matching the existing entries.
4. If it's a figure with real artwork, drop the image in `assets/` and use it as the hub card's `<img>` and/or the individual page's `.trick-media__panel` (see `figures/saturn.html` for the pattern) — otherwise both fall back to the ripple-icon tile automatically.
5. Run `python scripts/sync_pages.py` to regenerate the `auto:` sections everywhere the new page needs to show up: its own breadcrumb, the hub page's count/DD-range, the landing page's category-feature count/blurb/preview, and the "related tricks" list on every sibling page in the same category (including the new page's own, once it exists).
